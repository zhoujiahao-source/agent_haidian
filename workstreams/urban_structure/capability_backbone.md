# Capability Backbone — Six-Layer Spatial Model

## Definition

`Capability Backbone / 城市能力交换骨干` is the spatial + institutional armature that lets different districts discover, access, move, test, evaluate and publicly remember urban capabilities.

It is composed of six interlocking layers. No single layer is sufficient on its own.

## Layer 1 — Historical Memory

**Purpose:** connect railway heritage with the city's learning history without turning the project into retro railway decoration.

**Drawable actions:**

- Preserve/interpret verified railway-related traces and views once official heritage data is available.
- Use station / switch / mileage-marker logic as information design DNA for capability routing and status.
- Create `Landmark as Memory` nodes that record `CONTINUE / MODIFY / STOP / RETIRE` outcomes.
- Insert annual `City Version Release` displays into public places rather than a standalone technology museum.

**Current status:** concept is strong; exact heritage-control geometry remains Unknown.

## Layer 2 — Movement & Access

**Purpose:** make capability exchange reachable by foot, bicycle, accessible mobility and public transport interfaces.

**Drawable actions:**

- Reuse the old `ROAD-001` as a **candidate continuity axis**, not as a confirmed greenway alignment.
- Audit each `ROAD-002`–`ROAD-006` east-west axis against verified crossings before adoption.
- Prioritize universal-access continuity, safe crossings, resting intervals and transit transfer clarity.
- Add route redundancy: a network remains functional when one segment closes or a user cannot use digital navigation.

**Performance questions:** Can a wheelchair user make the same connection? Is there a non-digital route? Is a crossing legally and physically available? Can emergency/service access coexist?

## Layer 3 — Public Realm

**Purpose:** ensure the backbone is lived urban space rather than movement infrastructure.

**Drawable actions:**

- Sequence plazas, neighborhood interfaces, active ground floors, market/service edges, quiet gardens and event-ready spaces.
- Place `Public Capability Interface` at normal everyday destinations rather than requiring a special AI pavilion.
- Combine seating, shade, drinking water, restrooms, charging, accessibility help and human service desks where appropriate.
- Keep sensor-light zones and low-stimulation alternatives inside the main network.

## Layer 4 — Blue-Green Ecology

**Purpose:** integrate climate adaptation and ecological public life into capability testing.

**Drawable actions:**

- Treat Xiaoyuehe-related park/water public spaces as a candidate living test environment, subject to verified water/park boundaries.
- Use shade, infiltration, planting, water-sensitive design and heat-risk response as permanent public value before adding AI.
- Test low-risk ambient capabilities such as heat alerts, irrigation optimization or accessible route advice only with lawful/public/aggregate data.
- Avoid sensor saturation; environmental benefit must remain usable when digital systems are offline.

## Layer 5 — Capability Nodes

**Purpose:** provide places where people, organizations and districts can call, test, exchange and understand capabilities.

Candidate hierarchy is developed in `node_hierarchy.md`, but the backbone should always include:

- network-scale exchange hubs;
- district production / validation nodes;
- neighborhood public interfaces;
- reversible experimental nodes;
- memory / retirement nodes;
- professional-service exchange nodes;
- blue-green / resilience interfaces.

## Layer 6 — Event & Operations

**Purpose:** make the corridor change through the day, year and city-learning cycle.

**Drawable actions:**

- Daily: normal public services and low-risk ambient functions.
- Weekly/monthly: test windows, community review, developer clinics, market validation and public workshops.
- Annual: Jing-Zhang City Learning Assembly + Annual City Version Release.
- Lifecycle: failed/obsolete capabilities move to the Retired Capability Archive with reason and replacement history.

Operations should never imply that an event grants higher technological authority. Risk level, reversibility and public impact govern authorization.

## Six-layer overlay matrix

| Layer | Permanent carrier | Adaptive component | Experimental component |
|---|---|---|---|
| Memory | protected/verified heritage relation, durable archive locations | rotating city-version exhibition | temporary experiment/failure exhibit |
| Movement | accessible path/crossing/wayfinding foundation | seasonal routing, event management | temporary crossing demand test where lawful |
| Public realm | shade, seating, drainage, access | modular furniture, market/event kit | temporary service kiosk / prototype interface |
| Blue-green | soil/water/shade/ecological structure | seasonal planting/irrigation tuning | monitored reversible climate pilot |
| Capability nodes | power/data-ready civic room, human service point | changeable service modules | time-limited AI/robot/service prototype |
| Event/operations | stewardship, safety, complaint and audit process | annual/seasonal programming | sandbox rules for a specific pilot |

## Candidate backbone sections

The final drawing should not give the whole corridor one section. Use at least four section families:

1. **Heritage + slow mobility section:** quiet edge, retained trace / view, accessible route, low-tech interpretation, optional digital layer.
2. **Neighborhood capability interface:** active frontage + civic room + shade/seating + consent interface + human help.
3. **Research verification edge:** porous campus edge + controlled test yard + public observation line + emergency/manual override.
4. **Blue-green capability interface:** water/park edge + ecological buffer + accessible path + low-risk ambient service + sensor-light refuge.
5. **Market/night interface:** transit/commerce edge + flexible spill-out + service recovery desk + night safety/lighting logic.

## Backbone acceptance test

The Backbone is acceptable only if the Final Integration Agent can answer YES to all of the following:

- A person can physically move through meaningful parts of it without using an app.
- Each Three Areas / Two Wings unit exchanges a different capability through it.
- Railway history is spatially present but not reduced to themed decoration.
- Public Capability Interfaces have real physical hosts.
- Some segments can remain light-touch rather than requiring major construction.
- Permanent / Adaptive / Experimental layers are distinguishable.
- At least three representative sections show the backbone in cross-section.
