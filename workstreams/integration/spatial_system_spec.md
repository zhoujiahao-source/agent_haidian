# Spatial System Specification

## 0. Status

This document defines the **conceptual spatial system** to be translated into the formal package only after current geometry / allowed-design-space / source status are revalidated.

It does **not** define an official redline, statutory land-use plan, final parcel ownership, confirmed demolition, engineering feasibility or approved construction scale.

# 1. One-sentence spatial strategy

**以京张铁路历史连续性为场所记忆，以一条“城市能力交换骨干”串联三区两翼的差异化城市学习单元，把创新资源、公共空间、真实生活场景和可逆试验组织成一个能够持续生产、验证、交换和淘汰公共能力的城市网络。**

# 2. Capability Backbone is not one line

The Capability Backbone should be represented as a **stacked urban infrastructure**, not a decorative axis.

It contains at least five mutually reinforcing layers.

## Layer A — Memory Continuity

Purpose:

- preserve / interpret Jing-Zhang railway history;
- make the 1909 → 2026 → Future time sequence spatially legible;
- connect heritage traces with contemporary learning archives.

Possible spatial media, subject to real evidence:

- railway traces / station-related spaces / historic structures;
- material bands / milestone language;
- historical interpretation nodes;
- Retired Capability Archive relationship.

## Layer B — Public-Realm Continuity

Purpose:

- form a walkable / cycle-friendly / accessible sequence where possible;
- stitch fragmented parks, streets, station areas, communities and innovation districts;
- provide ordinary public life before any AI function is added.

Design test:

> If all AI technology is switched off, does the backbone remain a useful public-space and movement system?

If the answer is no, the design is too technology-dependent.

## Layer C — Capability Interface Network

Purpose:

- host differentiated Public Capability Interface nodes;
- enable residents to call or encounter public capabilities without understanding the underlying AI stack;
- support Ambient / Consent / Human Override layers.

## Layer D — Experiment & Learning Network

Purpose:

- host reversible test locations where allowed;
- publicly indicate test state, risk class, evidence status and responsible human authority;
- connect experiment results to the learning archive / annual version release.

## Layer E — Capability Exchange / Institutional Network

Purpose:

- link the three areas and two wings as a distributed production / validation / transfer system;
- connect talent, research, capital, IP, public services, markets and real-world scenes;
- represent not only movement but the **transfer conditions** for validated capability.

# 3. Three areas + two wings as distributed learning units

The final spatial design must not depict all five as equal generic smart districts.

## 3.1 众智园 — Capability Foundry / Validation Campus

### Primary role

**技术验证 / 全栈能力生产**

### Official alignment

- AI full-stack autonomous innovation system
- AI governance

### Spatial design questions

- Where can research capability meet controlled urban test conditions?
- Which spaces can support labs / demonstration / validation without becoming an isolated campus?
- How does the district connect to the Capability Backbone and real public scenes?
- Which facilities should be permanent, and which should be modular / reversible?

### Suggested spatial components

Subject to actual site evidence:

- capability validation hub;
- shared testing / demonstration spaces;
- developer / research commons;
- governance / audit interface;
- transition spaces between controlled test and real city.

### Secondary capabilities

- governance-method production;
- developer community;
- cross-area technical support.

## 3.2 北京 AI 原点社区 — Civic Learning Community

### Primary role

**社会反馈 / 人才社区 / 公共服务学习**

### Official alignment

- world-class AI innovation ecosystem

### Spatial design questions

- How can talent / research ecology coexist with everyday residential / community life?
- How does public service improve without turning the community into a permanent experiment subject?
- Where are consent, human service and community deliberation visible?

### Suggested spatial components

- community capability interfaces;
- civic feedback / co-design spaces;
- accessible everyday public services;
- talent / research / community mixing spaces;
- low-risk learning nodes.

### Secondary capabilities

- accessibility and inclusion review;
- community feedback;
- public-service design validation.

## 3.3 大钟寺 — AI-Native Urban Service & Market Test District

### Primary role

**市场验证 / AI-native 城市服务与商业**

### Official alignment

- AI-native business

### Spatial design questions

- What is genuinely AI-native about the service / business model rather than merely digital retail?
- How can new services improve public life and remain governable?
- How can commercial validation feed back into public-value review?

### Suggested spatial components

- mixed public-service / commercial interfaces;
- temporary service pilots;
- public-value display / feedback points;
- night-economy / event spaces compatible with everyday use;
- interface with railway / cultural memory where supported by site evidence.

### Secondary capabilities

- market feedback;

## 3.4 中关村科技服务翼 — Innovation Resource Exchange Wing

**创新资源 / 资本 / 知识产权 / 专业服务交换**

### Spatial design questions

- How do professional services become accessible to capability producers across the corridor?
- Where are exchange / matchmaking / knowledge-transfer spaces located?

### Suggested components

- innovation service nodes;

## 3.5 小月河场景赋能翼 — Living Urban Test Wing

### Primary role

**真实公共空间与城市场景测试**

### Official alignment

- AI+ scenario empowerment
- intelligent active city

### Spatial design questions

- How can riverside / park / neighborhood public life support low-risk reversible scenarios?
- How can climate, accessibility, mobility and community-service tests remain inclusive?
- How can tests be removed or modified without damaging ordinary public space?

### Suggested components

- climate / shade / heat-refuge interfaces;
- accessible-route testing;
- community and recreation nodes;
- event / night / emergency scenario routes;

# 4. Node hierarchy

The final node hierarchy should be spatially clear but not overcomplicated. Candidate hierarchy:

## N1 — Backbone Exchange Hub

Role:

- major multi-capability exchange;
- connects more than one learning unit / mode;
- public information about current city version and experiments;
- may host annual / major public events.

Design rule:

Must still work as meaningful public space without an event.

## N2 — District Learning Node

Role:

- expresses each area's primary capability;
- hosts local testing / feedback / transfer;
- connects district program to backbone.

## N3 — Neighborhood Capability Interface

Role:

- everyday public-service access;
- low-friction, inclusive and human-scaled;
- prioritizes ordinary needs over tech visibility.

## N4 — Experimental Node

Role:

- explicitly time-limited / reversible test;
- visible test status, risk tier and rollback / human authority;
- must have baseline and evaluation plan.

## N5 — Memory Node

Role:

- railway history / city-learning archive / retired capability / version record;
- connects technical history to civic learning.

## N6 — Emergency / Resilience Node

Role:

- supports heat, emergency, accessibility or service continuity scenarios;
- requires particularly clear non-AI fallback / Human Override.

A node can combine roles, but the final map must avoid creating dozens of indistinguishable icons.

# 5. East–west stitch

The official task explicitly requires east–west stitching. Final design should test multiple spatial mechanisms, not rely on one bridge gesture.

Potential toolkit, subject to evidence:

1. street / crossing continuity;
2. slow-mobility links;
3. public-space sequence across barriers;
4. station-area permeability;
5. program pairs on opposite sides of rail / major roads;
6. capability-interface pairs that make both sides functionally interdependent;
7. clear accessible routes;
8. green / shade continuity where site conditions allow.

Evaluation questions:

- Does the intervention shorten / simplify real public movement?
- Does it connect daily destinations, not just landmarks?
- Is it accessible to vulnerable users?
- Is it compatible with locked railway / road / heritage constraints?

# 6. North–south continuity

Potential toolkit:

- continuous public-space / green connections;
- movement across fragmented parcels / road systems where allowed;
- linked scenario nodes rather than isolated parks;
- cultural / memory route;
- multi-modal transfer logic;
- ecological / river relationship where appropriate.

The final diagram should distinguish **existing continuity**, **estimated / incomplete continuity**, and **proposed stitch**.

# 7. Permanent / Adaptive / Experimental spatial layers

## P — Permanent Infrastructure

Long-lived city value even if today's AI becomes obsolete.

Examples, subject to planning / engineering feasibility:

- accessible public-space connections;
- key landscape / shade / ecological infrastructure;
- robust public-service / community facilities;
- durable heritage-memory structures;
- open node infrastructure designed for future technology replacement.

## A — Adaptive Layer

Spaces / interfaces able to change program over time.

Examples:

- modular service zones;
- adaptable public-space furniture / utilities;
- flexible event / market / community-use surfaces;
- reconfigurable interface areas.

## E — Experimental Layer

Short-duration, reversible and explicitly governed.

Examples:

- temporary sensors / displays where legally appropriate;
- test service kiosks;
- temporary route guidance;
- small-scale climate / service prototypes;
- event-based public capabilities.

No Experimental layer should create a permanent dependency without passing review.

# 8. Public Capability Interface spatial rules

Every interface should answer:

1. What public need does this serve?
2. Is it Ambient or Consent?
3. What is the non-AI fallback?
4. Who can override / stop it?
5. What is visible to the public about its state?
6. What data are needed?
7. What is the experiment / service boundary?
8. What happens when the technology is retired?

# 9. Three landmark system

## L1 — 1909 Railway Memory

Spatial purpose:

- anchor the corridor in a real technical-history identity;
- reveal continuity between infrastructure, public confidence and national technical capability;
- avoid fake nostalgia or invented heritage geometry.

## L2 — 2026 City Learning Archive

Spatial purpose:

- publicly record experiments, changes, failures, public-value outcomes and city-version history;
- make governance physically legible;
- include successful and stopped projects.

## L3 — Future Experimental Station

Spatial purpose:

- host unresolved future-city questions;
- visibly separate speculation / experiment from settled public infrastructure;
- demonstrate reversibility and learning.

## Retired Capability Archive

May be integrated with L2 or located as a connected memory facility depending on real spatial evidence. It should be serious, accessible and curated as civic technical memory.

# 10. Drawing requirements derived from this spec

The future formal package should be able to draw at least:

1. Evidence-first site overview — existing city + uncertainty.
2. Capability Backbone layer stack.
3. Three areas + two wings capability specialization.
4. Node hierarchy and scenario network.
5. East–west / north–south stitch strategy.
6. Permanent / Adaptive / Experimental layer diagram.
7. Three key sections showing everyday public life + capability interfaces.
8. 1909 / 2026 / Future landmark sequence.
9. A time-based scenario orchestration diagram.
10. A 5 / 10 / 20-year adaptability diagram.

# 11. Spatial anti-patterns

Reject:

- a single glowing AI axis with no urban content;
- five equal bubbles for the five zones;
- generic smart benches / screens as the main public-space answer;
- a giant AI sculpture as landmark;
- precise building / parcel redesign unsupported by evidence;
- permanent tech hardware everywhere;
- public spaces that are useful only when an app / model works;
- scenario nodes without ordinary public-life value;
- heritage used only as graphic decoration;
- an axis that cannot explain actual east–west / north–south urban connections.

# 12. Spatial exit test

Before this spec is translated into canonical geometry, the integrator must answer:

- Which backbone components are real existing assets?
- Which are estimated / inferred?
- Which are new design proposals?
- Which official / locked constraints shape them?
- Which node types fit within allowed editable layers?
- What can be computed from geometry?
- What remains conceptual because official data are missing?

Only then should canonical geometry be modified.
