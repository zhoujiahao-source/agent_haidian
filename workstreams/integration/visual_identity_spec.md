# Visual Identity & Information Design Specification

## 0. Status

This document defines the **design direction** for the formal submission and future public-facing system. Exact fonts, colors, logo geometry and export assets must be tested in the required figures / A3 / A0 / HTML environment and must comply with licensing / repository constraints.

# 1. Visual thesis

**Public Service Aesthetic｜公共服务美学**

The visual system should communicate:

- trust;
- clarity;
- public access;
- system state;
- evidence / uncertainty;
- capability exchange;
- long-term civic use.

It should not communicate “AI spectacle”.

# 2. Visual DNA from Jing-Zhang railway

Use four railway-derived primitives without becoming retro railway branding.

## Double track / 双轨

Translate into:

- parallel existing / proposed information;
- public need / capability flow;
- Ambient / Consent dual layer;
- old / new technical eras.

## Station / 站点

Translate into:

- public capability node;
- exchange hub;
- learning unit;
- service interface.

## Switch / 道岔

Translate into:

- STOP / MODIFY / CONTINUE / SCALE decision;
- route / capability transfer;
- alternative / Human Override.

## Milestone / 里程标

Translate into:

- 1909 / 2026 / Future;
- city version numbers;
- capability lifecycle;
- annual learning record.

# 3. Logo — Open Node

## Concept

The logo should read simultaneously as:

- a station;
- an open interface;
- an exchange node;
- a capability call point;
- a civic hub.

## Geometry direction

Recommended exploration:

- a central open gap / entrance rather than a sealed circle;
- two or more lines approach / exchange / continue;
- node is not a “core” controlling all flows;
- can expand into a network pattern;
- remains legible at small wayfinding scale.

## Avoid

- robot head;
- brain;
- chip;
- spark / magic icon;
- infinity loop;
- generic neural network;
- corporate AI gradient logo;
- literal steam locomotive silhouette.

# 4. Identity hierarchy

The system should support:

1. Project main identity — one final Chinese + English name.
2. Capability Backbone identity.
3. Three areas + two wings.
4. Public Capability Interface node types.
5. Scenario / experiment states.
6. Annual City Version Release.
7. 1909 / 2026 / Future landmark family.
8. Retired Capability Archive.

Avoid creating a separate unrelated logo for every subsystem.

# 5. Core state systems

Color alone must never carry all meaning.

Use combinations of:

- color;
- line pattern;
- shape;
- label;
- icon;
- border / fill state.

## 5.1 Data evidence state

### Official

Visual cue:

- strongest / most stable evidence treatment;
- explicit `OFFICIAL` text / badge in detailed views.

### Verified

Visual cue:

- solid but distinguishable from official;
- `VERIFIED` label where needed.

### Derived

Visual cue:

- patterned / calculated visual treatment;
- method reference.

### Assumed

Visual cue:

- clearly provisional / hypothesis treatment;
- not visually stronger than Verified.

### Unknown

Visual cue:

- open / blank / unresolved symbol;
- do not visually “fill” unknown areas with fake completeness.

## 5.2 Drawing state

### Known

Existing / supported spatial evidence.

### Estimated

Derived / proxy existing condition.

### Proposed

Design proposal.

### Unknown

Evidence missing / unresolved.

Suggested non-color distinction:

- Known = solid line / fill;
- Estimated = patterned / interrupted treatment;
- Proposed = clear outline / directional / design overlay;
- Unknown = neutral open field / question marker in legend.

## 5.3 Experiment lifecycle state

Required labels:

- TEST
- MODIFY
- CONTINUE
- SCALE
- STOP
- RETIRED

Use switch / route logic rather than traffic-light metaphor only.

For example:

- TEST = entry / open switch;
- MODIFY = route bends / loops back;
- CONTINUE = line proceeds within boundary;
- SCALE = line expands to additional node(s);
- STOP = terminated track / closed endpoint;
- RETIRED = archived milestone / faded but readable trace.

## 5.4 Risk state

- LOW
- MEDIUM
- HIGH

Use explicit text / symbol and avoid relying only on red-yellow-green, especially for color-vision accessibility and because “green” can be misread as approved / safe.

# 6. Typography principles

## Chinese

Use a highly legible modern sans-serif / public-information style with full Chinese support and appropriate licensing in the production environment.

Hierarchy:

- H1: strong, concise project / chapter title;
- H2: system / spatial component;
- body: high legibility, moderate line length;
- data / tags: compact but not tiny.

## English

Use a compatible sans-serif with good numerals / technical labels.

## Bilingual layout

Do not duplicate every line at equal visual weight if it harms legibility. Use one clear primary-language hierarchy and an aligned secondary language according to formal package translation requirements.

Terminology must stay stable:

- Capability Backbone
- Public Capability Interface
- Urban Adaptation Rate
- Public Stewardship
- Annual City Version Release
- Retired Capability Archive

# 7. Color principles

Exact values should be tested later, but the system should use:

## Neutral civic base

- light / paper-like background for most diagrams;
- dark high-contrast text;
- restrained infrastructure / existing-condition neutrals.

## Limited functional accents

Use a small number of accents for:

- Capability Backbone;
- public-space / blue-green system;
- risk / experiment state;
- areas / learning units.

Do not give every concept a saturated color.

## Print resilience

Every key figure should remain understandable in:

- grayscale;
- low-quality printing;
- projector / screen;
- reduced A3 scale.

# 8. Map language

## Existing urban base

Visually quiet but legible.

Potential hierarchy:

1. site / key boundaries — only according to evidence status;
2. railway / major movement / water / green;
3. buildings / blocks;
4. public facilities / innovation actors;
5. proposal overlay.

## Capability Backbone

Show as a layered corridor / sequence rather than one thick neon line.

Potential techniques:

- main route + node sequence;
- parallel service / memory / public-realm strands;
- switch / transfer points;
- evidence-state labels.

## Three areas + two wings

Differentiate by:

- role icon / label;
- secondary accent;
- capability annotation;

Avoid five equal saturated blobs.

# 9. Node signage / ID system

Candidate public node code:

`JZ-[AREA]-[TYPE]-[NN]`

Examples are illustrative only:

- `JZ-ZZ-CAP-01`
- `JZ-XY-RES-03`
- `JZ-DZS-MKT-02`

Final codes must avoid conflict with official / schema IDs and should not enter machine-readable geometry unless needed / allowed.

Public-facing node information can include:

- node name;
- public function;
- current experiment / service state;
- AI-Off fallback;
- optional QR / digital detail;
- feedback / human-service route.

# 10. Annual City Version identity

Recommended format:

`Jing-Zhang City v2027`

or final project name + `v2027` after naming is fixed.

## Visual structure

Use milestone / track / changelog language.

Annual release visual categories:

- ADDED
- MODIFIED
- CONTINUED
- SCALED
- STOPPED
- RETIRED
- UNRESOLVED

The version graphic should appear in:

- annual report;
- City Learning Archive;
- major exchange hub;
- dashboard / HTML;
- annual assembly materials.

# 11. 1909 / 2026 / Future landmark identity

Do not make three unrelated brands.

Use one family with different temporal states:

## 1909

- archival / material emphasis;
- verified historical source / date prominence.

## 2026

- active version / learning records;
- current experiment / metric language.

## Future

- open / unresolved / experimental state;
- deliberately avoids visual certainty.

# 12. Required figure style

## site-overview.png

Purpose:

Evidence-first orientation.

Must show:

- real current spatial base;
- provisional / unknown limitations;
- key evidence sources / tags;
- no hero-image treatment.

## land-use-structure.png

Purpose:

Explain design structure and planning metrics.

Must show:

- clear land-use / public-space structure;
- Capability Backbone relationship;
- proposed vs known distinction.

## key-areas.png

Purpose:

Explain three areas + two wings as capability-learning system.

Must show:

- primary role per area;
- backbone exchange;
- important nodes;
- no equal-weight bubble diagram.

## mobility-bluegreen.png

Purpose:

Explain movement + east–west / north–south stitch + blue-green public realm.

Must show:

- existing / proposed connections;
- accessibility / public-space relevance;
- relationship to capability interfaces.

## metrics-evidence.png

Purpose:

Explain spatial metrics + evidence quality + city-learning metrics.

Must show:

- conventional geometry-derived metrics;
- uncertainty / evidence states;
- Urban Adaptation Rate framework;
- public-value five dimensions;
- no fabricated current values.

# 13. A3 booklet system

Recommended page rhythm:

1. strong thesis + evidence-oriented site introduction;
2. master structure;
3. three areas + two wings;
4. City OS learning protocol;
5. public-value metrics;
6. public capability nodes / scenarios;
7. ecosystem / cases;
8. public-space sections;
9. landmarks / culture;
10. operations / annual version;
11. 5 / 10 / 20-year evolution;
12. evidence / source / uncertainty summary.

Exact pagination depends on latest formal requirements.

# 14. A0 board system

A0 should not be a stretched A3 report.

Recommended hierarchy:

- one clear city thesis;
- one master spatial system;
- one governance / public-value loop;
- 2–3 high-value spatial enlargements / sections;
- one landmark / time narrative;
- concise evidence / metrics panel.

# 15. HTML / dashboard language

Offline HTML should feel like a civic system, not a product landing page.

Recommended navigation:

- Site
- Capability Backbone
- Learning Units
- Scenarios
- Public Value
- City Version
- Memory / Archive
- Evidence

Avoid:

- parallax / animation that hides information;
- inaccessible hover-only data;
- video backgrounds;
- generic AI particle effects.

# 16. Accessibility

Visual system must consider:

- color-vision differences;
- readable text size;
- high contrast;
- non-color state encoding;
- bilingual clarity;
- alt text / captions for digital outputs where supported;
- straightforward map legends.

# 17. Naming integration

Final main name remains **OPEN** during this workstream.

Naming criteria:

1. should communicate city / Jing-Zhang specificity;
2. should support the City OS / capability exchange thesis;
3. should not sound like a private technology product;
4. should coexist with fixed official three positionings;
5. should work in Chinese and English;
6. should support long-term version identity;
7. should not force `AI` into every subsystem name.

`Legible AI` may be retained as a sub-principle, for example `Legibility Layer`, if it improves transparency language.

# 18. Final visual anti-pattern checklist

Reject if the design depends on:

- cyberpunk neon;
- black background + glowing cyan as default;
- generic chip / brain graphics;
- abstract data particles instead of maps;
- unannotated atmospheric renders;
- giant screen walls;
- raw GIS screenshots;
- equal-weight information dumps;
- figures whose proposal layers look more “official” than known layers;
- color-only legends;
- tiny citation / evidence text unreadable in A3.

# 19. Deliverable test

A reviewer should be able to identify, within seconds:

- what is existing;
- what is estimated;
- what is proposed;
- what is unknown;
- where the Capability Backbone is;
- what each learning unit does;
- which state an experiment is in;
- how to find deeper evidence;
- why the visual language belongs to Jing-Zhang rather than any AI city.
