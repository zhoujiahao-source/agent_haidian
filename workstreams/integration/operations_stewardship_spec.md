# Long-Term Operations & Public Stewardship Specification

## Status

This is a **proposed governance / operating model** for competition design. It does not state that a named government body, university, company or community organization has committed to operate the system.

# 1. Operating principle

**Public Stewardship｜公共机构主导、社会参与**

The city may open innovation, but final responsibility for safety, data governance, risk authorization and public-value review cannot be outsourced to an AI vendor or platform.

# 2. Responsibility layers

## Layer 1 — Public Steward / 公共责任主体

Conceptual responsibilities:

- define public-interest objectives;
- approve governance rules;
- define / enforce risk authorization boundaries;
- protect basic service access and non-AI alternatives;
- require data / evidence compliance;
- convene or commission independent review;
- authorize STOP / SCALE according to applicable responsibilities;
- publish public-version records;
- preserve long-term city-learning memory.

The formal proposal should normally keep this role generic unless a specific real institution is supported by source and the wording does not imply commitment.

## Layer 2 — Professional / Independent Review

Potential participants, expressed as proposed roles:

- planning / urban-design professionals;
- safety / engineering experts where relevant;
- data / privacy / ethics experts;
- accessibility / inclusion reviewers;
- university / research reviewers;
- independent evaluators.

Function:

- challenge evidence;
- review risk / public-value methodology;
- audit selected high-impact cases;
- verify that scaling decisions are not based on vendor claims alone.

## Layer 3 — Capability Producers

Potential participants:

- universities;
- research institutes;
- companies / startups;
- open-source / developer communities;
- design teams;
- civic-tech contributors.

They may propose / build capability but do not automatically authorize deployment.

## Layer 4 — Community / Public Participants

Roles:

- identify problems;
- report barriers / service failures;
- participate in scenario definition;
- review impacts;
- object / appeal / request human service through appropriate processes;
- participate in annual city-learning public events.

Participation is not limited to surveys or spectacle.

# 3. Dual innovation entry

## Problem Track

`real issue → City Agent / public team diagnosis → evidence qualification → public challenge / scoped brief → proposals → risk authorization → sandbox / pilot → public-value review`

Purpose:

Make the city problem primary.

## Capability Track

`capability proposal → public-need traceability → evidence qualification → risk authorization → sandbox / pilot → public-value review`

Purpose:

Allow bottom-up innovation without letting the city become a testbed for technology with no real need.

## Gate shared by both tracks

A proposal does not proceed merely because:

- a model is new;
- a major company offers it;
- it attracts media attention;
- another city has deployed it.

It proceeds only when:

- a real need is defined;
- evidence / baseline are adequate;
- risk / consent / fallback are defined;
- spatial test scope is appropriate;
- public-value evaluation is possible.

# 4. Developer ecosystem

## 4.1 City Challenge Board

A public-facing list of verified / qualified urban challenges rather than generic hackathon themes.

Each challenge record should include:

- problem statement;
- affected groups;
- evidence / uncertainty;
- spatial context;
- constraints;
- public-value dimensions;
- data that can legally be used;
- risk boundary;
- what a successful test must prove.

## 4.2 Capability Registry

Stores validated capability modules / versions, their contexts, risk, public-value result and transfer limits.

## 4.3 Sandbox

Provides lower-risk validation before public pilots.

## 4.4 Documentation / Open Methods

Share:

- problem definitions;
- permitted public datasets / data methods;
- test protocols;
- metric formulas;
- failure lessons;
- non-sensitive reusable code / methods where licensing permits.

## 4.5 Contribution Credit

Recognition should include:

- useful problem discovery;
- high-quality data / method contribution;
- accessibility / safety review;
- a well-documented STOP decision;
- reusable capability;
- failure documentation;
- public-space / service co-design.

Do not reward only successful SCALE outcomes.

# 5. Community participation model

## 5.1 Problem reporting

Provide digital and non-digital routes to surface:

- accessibility barriers;
- service mismatch;
- public-space discomfort;
- confusing interfaces;
- failure / harm;
- new needs.

## 5.2 Affected-group review

For scenarios with meaningful impact on a group, include that group's review before scaling where appropriate.

Examples:

- wheelchair users for accessible-route systems;
- older residents for digital public-service handoff;
- nearby residents for night-use scenarios;
- frontline workers for service automation.

## 5.3 Objection / correction

Public interface should not only collect positive “experience feedback”. It must allow:

- correction of wrong information;
- objection / complaint;
- request for human service;
- reporting of access / exclusion problems.

## 5.4 Community observatory

A proposed light-weight civic observation mechanism could periodically review:

- what is being tested locally;
- who benefits / bears burden;
- whether experiments have exceeded their promised end date;
- whether Human Override remains available;
- whether failure / complaint data are visible.

# 6. Operating cadence

The city learns continuously rather than waiting for one annual event.

## Continuous

- problem detection;
- low-risk monitoring;
- active-pilot observation;
- complaints / overrides;
- incident logging;
- source / evidence updates.

## Monthly / scenario-appropriate

- pilot operational review;
- data-quality check;
- stop-condition check;
- capability-registry updates.

Actual frequency should match risk / scenario rather than one arbitrary schedule.

## Quarterly — City Learning Review

Proposed agenda:

1. active pilot status;
2. STOP / MODIFY / CONTINUE / SCALE decisions;
3. vulnerable-group outcomes;
4. audit / incident / complaint summary;
5. capability-transfer proposals;
6. unresolved problem list;
7. upcoming public / developer challenge needs.

## Annual — Jing-Zhang City Learning Assembly

Public event + accountability institution.

# 7. Jing-Zhang City Learning Assembly

## Purpose

Not a standard tech conference.

It combines:

- city operating review;
- public accountability;
- urban-design / AI-governance forum;
- developer / research exchange;
- public cultural event;
- railway / technical-history narrative;
- next-year challenge launch.

## Core ritual

**Annual City Version Release｜年度城市版本发布**

Example format, clearly future / proposed:

`Jing-Zhang City v2027`

The release publishes:

- Added — new validated capability / public-space or service layer;
- Modified — capability or spatial / governance rule changed after review;
- Continued — still testing, not yet scaled;
- Scaled — expanded after successful revalidation;
- Stopped — intentionally ended;
- Retired — previously active capability removed / replaced;
- Unresolved — important city problem still without an adequate solution.

# 8. Annual City Version Release content contract

Every annual public version should include:

## 8.1 Public-value summary

- key improvements;
- equity / vulnerable-group summary;
- safety / privacy / environment / cost issues;
- UAR if a valid observed dataset exists;
- otherwise a transparent explanation of unavailable / incomplete metrics.

## 8.2 Capability changelog

- version;
- area / node;
- problem;
- decision;
- evidence status;
- major lesson.

## 8.3 Failure / STOP chapter

Mandatory, not optional.

Show:

- why cases were stopped;
- what harm / cost was avoided;
- what changed in future rules.

## 8.4 Retired capability chapter

Show:

- obsolete / replaced systems;
- transition / fallback;
- archive / hardware-disposal or reuse where relevant.

## 8.5 Next-year challenges

Prioritize unresolved real problems, not sponsor themes.

# 9. Event program architecture

Possible annual program:

## Day / Module A — City Release

- formal public changelog;
- public-value metrics;
- STOP / retired cases;
- next-year challenges.

## Module B — Urban Learning Forum

- planning / governance / responsible AI discussion;
- comparative international city cases;
- professional / community review.

## Module C — Capability Exchange

- validated capability demonstrations;
- transfer / revalidation clinics;
- developer / researcher collaboration.

## Module D — Public City Festival

- railway / AI culture route;
- family / community public-space program;
- archive / landmark activities;
- public discussion / non-digital participation.

The festival cannot replace the accountability release.

# 10. Retired Capability Archive governance

## Entry threshold

Not every software update becomes a museum object. Archive significant cases when they:

- materially affected public service / space;
- created an important lesson;
- represented a major technical generation;
- failed in an instructive way;
- changed governance rules;
- have meaningful physical artifact / public memory.

## Archive governance

Record:

- provenance;
- version;
- public-value history;
- incident / failure summary where public;
- reason for retirement;
- replacement / fallback;
- preservation / disposal decision;
- public interpretation.

## Ethical rule

Do not display personal / sensitive user data or shame individuals / teams. Preserve system lessons rather than turning failure into spectacle.

# 11. 5-year roadmap

## Objective

Prove the City OS as a repeatable governance / spatial-learning method.

Priorities:

- establish basemap / evidence standards;
- build core Capability Backbone public-space / interface prototypes where feasible;
- run limited scenario portfolio;
- establish capability / experiment registry;
- publish initial annual versions;
- create first learning archive;
- establish developer / community participation.

Success condition:

The system can stop weak pilots as confidently as it scales strong ones.

# 12. 10-year roadmap

## Objective

Turn validated learning units into a mature exchange network.

Priorities:

- cross-area capability transfer / revalidation;
- strengthen permanent public-space / mobility / accessibility backbone;
- mature independent audit / public participation;
- archive multiple technology generations;
- international urban-learning exchange;
- update physical interfaces without major reconstruction.

Success condition:

The corridor can replace technology layers while retaining public-service / spatial continuity.

# 13. 20-year roadmap

## Objective

Preserve **Urban Capability Exchange Network** after today's AI stack is obsolete.

Priorities:

- open interfaces / replaceable technology;
- institutional memory;
- physical public-space continuity;
- technical-culture archive;
- new technology entry through the same public-value / risk / test logic;
- retirement of obsolete systems without service loss.

Success condition:

The corridor is still useful if “AI” is no longer the relevant technology label.

# 14. Institutional risk register

## Risk A — Vendor capture

Mitigation:

- public-need gate;
- open / documented interfaces where feasible;
- transferability / exit planning;
- no vendor owns public authorization.

## Risk B — Permanent pilot syndrome

Mitigation:

- end date / review date required;
- capability review-age metric;
- annual version release exposes unresolved status.

## Risk C — Participation theater

Mitigation:

- objection / correction / Human Override channels;
- affected-group review linked to SCALE decision;
- publish how feedback changed design.

## Risk D — Failure concealment

Mitigation:

- mandatory STOP / failure chapter;
- failure-documentation metric;
- archive rules.

## Risk E — Digital exclusion

Mitigation:

- AI-Off / non-digital fallback;
- digital opt-out parity metric;
- frontline human-service capacity.

## Risk F — Metric gaming

Mitigation:

- raw component measures;
- vulnerable / worst-case outcomes;
- independent review;
- no UAR without denominator / decision distribution.

## Risk G — Institutional ambiguity

Mitigation:

- formal implementation deepening must assign legal responsibilities clearly;
- competition package stays conceptual and avoids invented commitments.
