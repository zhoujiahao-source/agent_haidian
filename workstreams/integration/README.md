# Integration Workstream README

## Purpose

This directory is the single-source integration workstream for upgrading the existing `jingzhang-legible-ai-belt` formal submission into the current **City OS / Capability Backbone / Urban Capability Exchange Network** concept without destroying the previous validated package.

The integration branch must always begin each work session by re-reading the repository's current `README.md` and the latest upstream submission skill. The upstream repository is a living task environment; do not freeze rule assumptions to an old commit.

## Formal package rules to keep visible

A reviewable package must follow the current official skill, including at minimum:

- `package_type = professional_design_package`
- `package_state = ready_for_review`
- `submission_stage = formal` only as legacy compatibility when required by schema
- real public or user-cleared data only
- all organizer tasks mapped in `compliance_matrix.json`
- all `agent.1`–`agent.6` mapped and explained in `proposal.md`
- mandatory professional standards covered in `standard_matrix.json`
- required formal depth complete in `design_depth_matrix.json`
- evidence tags in proposal using the repository-prescribed `[source:...]`, `[standard:...]`, `[depth:...]`, `[data:...]`, `[metric:...]` syntax
- required five evidence figures
- offline HTML visualization
- A3 and A0 PDFs
- rendered proposal HTML
- provisional geometry explicitly marked and never described as an official redline

## Integration authority order

2. verified real-world evidence
3. geometry
4. metrics
5. matrices

7. proposal narrative

## Data contract

All important evidence must be classified as one of:

- `Official`
- `Verified`
- `Derived`
- `Assumed`
- `Unknown`

All map / drawing claims must be visibly distinguishable as:

- `Known`
- `Estimated`
- `Proposed`
- `Unknown`

Source conflicts are recorded rather than silently overwritten.

- parcel ownership

## Upgrade sequence

### Phase 0 — Preserve baseline

Do not rewrite the old validated submission in place. Keep the old formal branch as a rollback point.

### Phase 1 — Evidence and conflict audit

Create:

- `integration_conflict_matrix.md`
- `baseline_audit.md`
- `source_gap_register.md`
- `official_task_coverage.md`

Record what the old package already satisfies, what conflicts with the new constitution, and what remains unsupported.

### Phase 2 — Concept-to-space conversion

Resolve:

- final naming hierarchy
- Capability Backbone spatial definition
- three-area / two-wing capability specialization
- permanent / adaptive / experimental spatial layers
- public capability node hierarchy
- 1909 / 2026 / Future landmark system

### Phase 3 — AI governance and metrics

Resolve:

- risk tiers
- authorization matrix
- experiment lifecycle
- Human Override
- public-value framework
- Urban Adaptation Rate formula and status
- anti-gaming and audit rules
- cross-area capability transfer rules

### Phase 4 — Scenarios / personas / ecosystem / culture / operations

Produce sufficient structured content for all `agent.2`–`agent.6` minimums.

### Phase 5 — Machine-readable package

Update geometry, metrics, matrices, sources, assumptions and manifest before final prose / visual outputs.

### Phase 6 — Human-readable proposal and figures

Rewrite proposal around one coherent story. Remove competing headline concepts. `Legible AI` may survive only as a governance / information-design principle if useful; the core is City OS + Capability Backbone + public-value learning.

### Phase 7 — Render and validate

Follow the latest commands from `SKILL.md`. At the time this integration README was written, the official flow includes installing the skill / requirements and running the repository-provided render, finalize, self-check and participant preflight scripts. Never assume command names if upstream has changed; re-read the skill first.

Repair until formal self-check is PASS or remaining warnings are explicitly non-blocking organizer data gaps.

## Naming rule

Do not allow multiple competing project names in the final package. During integration, candidate names may be recorded, but only one Chinese main name + one English main name may remain as the submission identity.

## Visual rule

Use **Public Service Aesthetic**, not tech spectacle. Required figures must remain evidentiary and spatial. The Open Node logo, railway double-track / station / switch / milestone visual DNA, risk / evidence / experiment-state legends and city-version identity should form one information system.

## Required final verification questions

A reviewer must be able to answer from the package:

1. What is actually on the site today?
2. Why is Jing-Zhang uniquely suited to this proposal?
3. Where and what is the Capability Backbone?
4. What does each of the three areas and two wings do?
5. How does AI enter a real urban decision safely?
6. What can an ordinary resident call or experience?
7. Who can stop the system?
8. What is the new measurable planning / governance contribution?
9. Where are the three major memory / future landmarks?
10. How does the city operate after the competition?
11. Which data are known, estimated, proposed or unknown?
12. Which claims can be reproduced from geometry / metrics / sources?

## Definition of done

The integration is not done when prose is persuasive. It is done when:

- the concept is spatially explicit;
- all six taskbook tasks are covered;
- metrics are reproducible or honestly marked unknown;
- evidence provenance is auditable;
- all required deliverables exist;
- derived visuals match machine-readable data;
- provisional constraints are disclosed;
- formal validation passes;
- CI passes after push;
- remaining warnings are clearly documented.
